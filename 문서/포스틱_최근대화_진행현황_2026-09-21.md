## 3. 대화 내용 분류 요약

### A. 작업자 중심 UX 및 정보 구조

주요 결정:

- 대상 사용자를 로봇 제어 전문가가 아닌 현장 작업자로 정의했다.
- 첫 화면에는 상태, 원인, 다음 행동만 표시하고 `plan_id`, `reason_code`, Capability Profile, 원시 측정값은 상세 또는 기술 정보로 내렸다.
- 내부 판정값 `PASS/BLOCK/ASK`는 각각 `안전 확인됨/실행 차단/추가 확인 필요`로 번역한다.
- 정상 상태의 온도 같은 연속값은 숫자를 숨기고, 주의·위험부터 실제값과 임계값을 표시한다.
- System status는 상단에서 `3/4 정상`처럼 요약하고 서비스별 상세는 진단 화면에 둔다.

관련 산출물:

- `문서/상태매트릭스_포스틱.md`
- `문서/기획서_템플릿(포스틱).md`
- `dashboard/src/App.jsx`
- `dashboard/src/styles.css`

### B. 명령·확인·차단 흐름

최종 합의 흐름:

1. 자연어 명령 입력
2. `동작 준비 → 안전 규칙 확인 → 가상 동작 확인`
3. 정보가 부족하면 질문을 0~N회 반복
4. 위험하면 실행을 차단하고 명령 수정만 허용
5. 모든 검증을 통과하면 실행 직전 최종점검 1회
6. `이대로 실행` 승인 후 로봇에 전달

추가 원칙:

- 질문은 승인이 아니라 부족한 정보를 채우는 단계다.
- 차단 상태에는 우회 실행 버튼을 제공하지 않는다.
- 계획, 로봇 상태 또는 판정 유효기간이 바뀌면 기존 승인을 무효화한다.
- 퍼센트 진행률보다 3단계 체크리스트를 기본으로 사용한다.

### C. STOP과 안전 상태

구분한 정지 개념:

- 물리 E-stop: 현장 안전회로이며 원격 해제 불가
- UI STOP: 실행 취소 요청이며 물리 E-stop을 대체하지 않음
- 관리자 중지: 새 작업 배정을 막는 운영 기능이며 현재 동작을 즉시 멈추는 기능이 아님
- 보호정지와 가드 상태: 별도 원인과 복구 절차 표시

복구 원칙:

- 자동 재개 금지
- 원인 확인 → 현장 리셋 → 상태 재검증 → 실행 재승인
- STOP 요청 접수와 실제 로봇 정지 확인을 별도 상태로 관리

UI에서는 이 구분이 표현돼 있다. 그러나 기존 ROS 실행 코드의 `stop`은 남은 스텝을 중단하는 플래그 수준이며, 현재 실행 중인 ROS 2 Action의 취소와 실제 정지 완료 확인 경로는 완성되지 않았다.

### D. 로봇 관리·기록·진단·설정

로봇 관리:

- 목록 + 선택 상세 패널 구조
- 기본정보, 셀, 도구, 지원 스킬, 운용 가능 여부 우선 표시
- 도구 이력과 프로파일 버전은 하위 탭
- 관리자 중지·재개는 일반 제어 및 STOP과 분리
- 2대 MVP에서는 즐겨찾기 UI를 제외

기록:

- 명령 1건을 기준으로 계획 → 검증 → 허가 → 실행 타임라인 표시
- STOP은 정상 단계가 아니라 실행 도중 삽입된 중단 이벤트로 표현
- 검증 결과와 실행 결과를 별도 필터 축으로 유지
- 기본 화면에는 사람이 읽는 설명을, 원문 JSON과 코드는 기술 상세에 배치

진단:

- 서비스명보다 `문제–작업 영향–조치`를 우선 표시
- 정상 서비스도 보이되 장애와 경고를 위로 정렬
- MVP에서는 복잡한 시계열 그래프 대신 실패 이벤트 목록 사용
- 원시 샘플은 문제가 있을 때만 제한된 범위로 제공

설정:

- 개인·운영·안전/권한 구역 분리
- 작업자·관리자·안전관리자별 노출 차등
- 안전 임계값은 작성 → 검사 → 승인 → 적용예약 → 적용 상태 흐름으로 설계

### E. 대시보드 디자인과 Figma 비교 화면

대화 흐름:

1. 기존 대시보드에 카드 위계, 숫자 크기, 온도 게이지, 상태 요약과 대비를 보정했다.
2. 실제 Figma 파일을 직접 생성할 수 없는 세션에서는 생성했다고 주장하지 않고 작업을 중단했다.
3. 이후 제공된 디자인 분석을 기준으로 React 내부에 `/settings-figma` 비교 라우트를 만들었다.
4. 같은 구조를 현황·로봇관리·기록·진단까지 확대했다.
5. 다크 통합 사이드바 + 중앙 명령 패널 + 우측 본문의 3열 구조로 정리했다.
6. 기존의 두꺼운 테두리·강한 그림자를 줄이고 12~16px 라운드와 옅은 테두리로 통일했다.

현재 비교 라우트:

- `/overview-figma`
- `/robots-figma`
- `/history-figma`
- `/diagnostics-figma`
- `/settings-figma`

주의: 이는 Figma 디자인을 참고한 React 비교 화면이다. 실제 Figma 파일 안의 컴포넌트·변수·오토레이아웃이 완성됐다는 의미는 아니다.

### F. 기술 아키텍처

문서상 합의된 목표 구조:

- REST: 명령과 조회
- SSE: 로봇 상태, 알림, 검증 진행 이벤트
- FastAPI와 ROS 2 `rclpy`: 별도 프로세스
- 브라우저에서 ROS 2/DDS 직접 접근 금지
- PostgreSQL 기반 제어권 lease
- 명령 멱등성
- 실행 직전 TOCTOU 재검증
- 상태 데이터 age와 시간 동기화 표시
- LLM 및 일반 명령 큐와 분리된 STOP 우선 경로

현재 기존 `Fourstick/api_server.py`는 FastAPI와 `rclpy`를 한 프로세스에서 직접 사용한다. 따라서 문서에서 확정한 최종 구조로 아직 분리되지 않았다.

### G. 보안·DB 검토

대화에서 확인된 핵심 위험:

- 프런트엔드에만 권한 검사 구현
- 클라이언트의 `organization_id`, `role`, `robot_id` 신뢰
- 조직 경계가 없는 전역 role
- 비원자적인 lease 갱신
- 중복 명령 및 TOCTOU
- STOP 요청 ACK를 실제 정지로 오인
- DB 명세 표에는 있지만 실제 SQL에는 없는 FK·UNIQUE 제약

반영된 항목:

- `diagnostic_exports`는 완료 전 URI/checksum이 NULL이고 완료 상태에서만 필수인 CHECK 조건이 기획서에 반영됐다.

남은 항목:

- `organizations`, `organization_memberships`
- 제어권 lease와 fencing token
- `commands.client_request_id` 실제 UNIQUE
- `ref_versions` 5종과 `snapshot_hash` 실행허가 계약
- 조직 범위 FK·UNIQUE
- 안전 임계값 변경 상태머신의 DB 제약

### H. LLM·방언·Task Plan 평가

완료된 평가:

- 5개 후보 모델 비교
- JSON 파싱 성공률과 슬롯 정확도를 분리 측정
- JSON Schema 구조화 출력 적용
- 빈 배열 회피를 위한 `minItems: 1` 추가
- Qwen3 8B를 1순위 후보로 선정

기록된 최종 Qwen3 결과:

- JSON 파싱 성공률: 95%
- 평균 슬롯 정확도: 0.786

중요한 해석:

- 구조화 출력은 JSON 형식 성공률을 높이지만 명령 의미와 슬롯 정확성을 보장하지 않는다.
- 실제 채택 전에는 현장 명령 holdout, 오류 유형, 지연시간, 라이선스와 하드웨어 조건을 다시 확인해야 한다.

4. 실행허가 계약, 멱등성, lease, TOCTOU를 DB 제약과 서버 로직으로 구현한다.
5. STOP을 ROS 2 Action 취소 및 실제 정지 확인 경로로 만든다.
6. 한 개 대표 명령을 음성 → 계획 → 검증 → 시뮬레이션 → 승인 → 실행 → 기록까지 E2E로 통과시킨다.

이 여섯 단계가 끝나면 “디자인이 완성된 데모”에서 “통제된 환경에서 동작하는 MVP”로 넘어갔다고 볼 수 있다.
